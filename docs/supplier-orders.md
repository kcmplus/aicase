# 手机订单推送至设备

更新：2026-11-06。以下区分本地代码、供应商真实创建／查单验证和待验收的执行能力；部署与真机验收分别记录。

## 已确认流程

仅**设备现场自取**进入此流程。快递／空运进入独立配送履约，不绑定设备、不推单、不调用 free。当前配送运费、收货信息和发货规则尚未接通，选择配送仅保存草稿，不创建可付款订单。

先扫码：确认设备和商品模板 → 创建我方订单、交付打印文件 → 服务端核验付款 → 后端调用供应商 saveOrder → 手机显示「立即打印」。后扫码：无目标设备的已付订单先保留；到现场扫码核对设备和模板，明确确认后交付文件并推单。

用户点击「立即打印」后，我方服务端核验订单，调用供应商**商家自营支付登记**，客户不重复付款。已按文档接入修改支付状态及订单查询；真实写入由 `SUPPLIER_PAYMENT_ENABLED` 控制，默认关闭。关闭时按钮不可用、确认返回 503；开启后先查单并持久化单次记录，再写入和回查。

供应商云端订单同步至 Rust 原队列。独立内嵌页仅读本机 Tauri / Rust 数据，展示二维码、订单、效果图与真实进度；不请求我方服务器，不调用 free 或本地 create_order，不放交互按钮。

## 手机接口

所有订单接口使用已有的 `X-Order-Key` 校验所有权，已登录客户的写请求同时校验 CSRF。客户端不能提交已付款标记、供应商订单号、密钥或远程文件 URL。

| 接口 | 参数与作用 |
| --- | --- |
| `POST /api/v1/store/orders/{reference}/device/` | 仅 pickup 订单。 JSON：`device_id`、`shop_id` 字符串，`inventory_item_id` 整数。必须与机型和有效库存匹配。`accept_template:true` 表示客户已确认设备机型预览，允许首次绑定时冻结该设备模板；后续必须按服务端模板渲染。重复绑定同一设备返回原记录。 |
| `POST /api/v1/store/orders/{reference}/print-files/` | multipart：`print_image`、`preview_image`。两张 PNG 均须匹配订单模板画布尺寸，各最多 4 MB。重复上传相同文件允许，禁止替换已交付文件。 |
| `GET /api/v1/store/orders/{reference}/` | 返回 `fulfillment_type`，并含 `fulfillment`：状态、设备、提示、历史确认、能否放行及 `release_available`。能否确认由真实付款、商家／设备归属、退款、取消状态及服务端开关共同决定；云端原始状态和最近核实时间独立保存。无设备绑定时为 null。 |
| `POST /api/v1/store/orders/{reference}/confirm-print/` | JSON：`{"confirm":true}`。先校验现场自取、归属、付款、退款与推单状态；开关关闭时返回 503；开启后以服务端订单号／金额进行单次自营支付登记，重复或超时不重放。客户端不可传 `pay_money`、`trade_no` 或 `pay_type`。 |
| `POST /api/v1/store/orders/{reference}/fulfillment/` | JSON：`{"fulfillment_type":"pickup","confirmed":true}`。仅将未绑定供应商订单、未进入设备流程、无有效退款的 pending／paid 历史未分类订单明确确认为自取；同值重复返回原记录。已推单等历史订单须人工核实。 |

新订单保存 `fulfillment_type=pickup`；为兼容旧客户端，新创建请求未传该字段时仍按 pickup 创建，按用户 2026-11-06 最新确认，迁移 0028 将历史 `unspecified` 补为 `pickup`，模型也默认 pickup。明确选过 courier／air 的记录不变，迁移不改付款／退款、设备绑定、订单版本和打印放行记录。默认现场自取不等于已经确认目标设备或允许开印。已退款／取消订单不再显示配送方式选择提示。新建 courier／air 及非 pickup 订单进入收银台均返回 409。

绑定后缺少文件时不允许进入付款收银台。已明确现场自取但尚未绑定设备的订单仍允许先付款。演示及支付渠道测试订单均不自动发送至真实设备。

打印图使用模板尺寸合成，不能把原始照片作为打印图。`product_pic_url` 与 `picture_origin_url` 均传最终打印图；`picture_effect_url` 为预览图。PNG 存在数据库，不写入公开 media 目录。供应商通过 HTTPS 随机短路径 PNG 链接读取文件，提交后 72 小时有效，每轮手动重试轮换地址；无需签名字符串或登录。旧签名地址仍限时兼容。设备超过此时限仍需下载的行为须与供应商确认，不能为刷新地址重复创建订单。

## 推单任务与配置

默认关闭真实远程写入。部署和联调通过后，推单使用以下服务端配置；本次不修改服务器开关：

```dotenv
SUPPLIER_ORDER_ENABLED=1
SUPPLIER_ORDER_PUBLIC_URL=https://aicase.chunpat.cc
SUPPLIER_PAYMENT_ENABLED=0
SUPPLIER_ORDER_STATUS_VERIFIED=0
```

公网 URL 是固定源地址，不使用客户端 Host 或传入 URL。商家凭证仍填后台「设备连接配置」，无需另配 H5 Authorization。

旧 `SUPPLIER_PRINT_RELEASE_ENABLED` 及 `TERMINAL_ALLOWED_ORIGINS` 配置已不再使用，无法靠旧开关恢复终端领取。新支付开关默认关闭，启用会实际修改供应商订单状态并可能开印；本轮没有启用服务器开关。

已付款状态由现有支付签名通知及渠道查询确认。任务仅扫描已明确 pickup、已经付款且设备／文件齐全的记录，因此付款与文件交付的先后顺序均可覆盖，不依赖用户停留在付款返回页。

```sh
python manage.py dispatch_supplier_orders
```

每次推单最多检查 20 单，并查询最多 20 笔在途供应商单；每笔状态读取至少间隔 10 秒，失败保留上次结果。状态变化排入设备库存只读刷新，同设备合并，失败不清空库存、不重发打印。dev/prod 的打包与部署脚本已包含 `aicase-{环境}-supplier-orders.timer`：每批结束 5 秒后再运行，系统服务不重叠；部署时先停止该任务，迁移/备份期间不推单。本轮未执行服务器部署。任务执行前再检查设备启用状态、库存时效、商品映射、模板版本、付款和退款。没有锁库存，也不自行扣库存。

## 防重复与结果核实

状态：`draft` → `prepared` → `submitting` → `submitted` / `rejected` / `unknown`。`rejected` 只在用户手动确认后重新进入 `prepared`；`unknown` 必须先核实。

业务号（毫秒时间戳 + 六位随机数字）首次绑定时生成并持久化。推单在远程调用前提交 `submitting`，并发进程锁定同一我方订单；超时、非预期响应、HTTP 错误及中断后的过期 submitting 均保留为 unknown，不自动重发。请求不跟随重定向，响应限大小，不记录密钥、签名文件链接或原始响应。

实际创建成功返回 HTTP 200、code=200，现仅接受这一成功码，并校验有效正数 id、非占位 trade_no，以及返回的业务号、设备和商品（若包含）。文档 code=0 示例不再作为成功条件。重复业务号和超时查单语义仍待供应商确认，不以重复创建来试探。支付更新结果不明时，按已有 trade_no 查询核实；创建本身超时且没有 trade_no 时，尚未确认按 business_number 查询的语义，仍需人工核实，不重复创建。

后台退款阻止推单与确认。历史领取或结果未知的放行记录继续保留：停用接口不会清除它们，也不会自动允许退款、重推或重新开印；先人工核实供应商执行结果。

### 状态定义与临时映射

| 字段 | 数值与解释 | 依据 |
| --- | --- | --- |
| `status` | 4：已取消 | 用户明确确认；只读查询原测试单也返回 4 |
| `pay_status` | 暂按 0：未支付，1：已支付理解 | 临时假设；程序仍以冻结实付金额、币种和订单身份回查，不仅凭这个值放行 |
| `print_status` | 0：尚无完成反馈；1：打印成功；其他值待确认 | 2026-11-10 用户确认 1=成功 |
| `shipment_status` | 0：尚无完成反馈；1：出货成功；其他值待确认 | 2026-11-10 用户确认 1=成功 |

`SUPPLIER_ORDER_STATUS_MAP` 配置打印／出货映射；`SUPPLIER_ORDER_STATUS_VERIFIED=0` 时保留原始数值和临时阶段供后台核对，不据此把真实订单推进至已出货、不据此解除在途退款保护。取得供应商确认／打样证据后再启用 verified。确认的取消状态 4 始终生效；退款仍需原路处理，不将供应商取消假装成顾客已退款。若已存在物理执行进度或取消信息过期，先核实执行结果。

## 2026-11-10 · 两端统一打印进度

- 后台列表、详情及手机订单列表、详情共用服务端 `order_progress` 展示结果，付款、打印、退款分开显示。后台按待处理、打印／出货中、已出货、异常／待核实、关闭类筛选；筛选与展示使用同一数据库条件，不从付款状态猜测物理进度。
- 打印中、已打印等待出货、出货中、已出货分别展示。物理阶段仅接受付款已核实且 `phase_verified` 的供应商快照；取消状态 4 优先。未核验、未知码或不匹配付款不能显示确定性打印／出货完成。旧记录不补造历史事件时间，也不把出货自动变成已取件。退款展示独立，不能抹掉已确认的物理反馈。
- 新增只读 `GET /api/v1/store/orders/<reference>/progress/`，沿用浏览器订单所有权校验；后台对应 `GET /api/v1/admin/orders/<id>/progress/` 沿用订单查看权限。响应不包含设计快照、原图或供应商访问凭据，不查询或写入供应商，不触发推单、付款、打印或退款。
- 两端详情每 5 秒、列表每 15 秒读取我方最新快照，页面隐藏暂停、返回立即刷新，无重叠请求。详情的已出货／取消等终态暂停轮询，退款处理中继续刷新；保留手动刷新。后台备注编辑不因轮询重置，关闭详情后停止请求；手机过期页面的迟到响应不能覆盖新页面或操作结果。
- 超过 60 秒没有成功设备反馈时标注延迟；失败保留最后已知状态与反馈时间，不能将刷新时间当成打印发生时间。供应商定时查单继续使用既有任务，和五分钟库存同步独立。
- 本地验证采用模拟反馈检查 390 像素手机订单与详情、桌面后台列表与详情；模拟的打印／出货状态不是实机证据。上线仍保持状态映射核验开关不变，实际任务状态及部署结果另行核对。
